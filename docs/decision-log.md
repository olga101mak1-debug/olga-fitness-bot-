## Записи

### 2026-07-17 — AI-провайдер: Claude, а не OpenAI

- Контекст: нужен основной AI-движок для анализа и диалога с пользователем.
- Решение: Claude (Anthropic) — основной инструмент; уже есть рабочая интеграция (`claude_ai.py`).
- Почему так: интеграция уже работала на момент решения.
- Альтернативы: OpenAI — используется отдельно, только для распознавания речи (Whisper API), не для диалога.
- Когда пересмотреть: если качество ответов Claude перестанет устраивать для этого сценария.

### 2026-07-17 — Инфраструктура MVP: SQLite вместо PostgreSQL + Redis

- Контекст: нужна БД для персонального бота одного пользователя.
- Решение: SQLite на MVP-этапе, слой БД скрыт за интерфейсом.
- Почему так: проще и дешевле в хостинге для одного пользователя; апгрейд на Postgres возможен позже без переписывания бизнес-логики.
- Альтернативы: PostgreSQL + Redis — отклонены для MVP как избыточные.
- Когда пересмотреть: если появится больше одного пользователя или вырастут требования к параллельным записям.

### 2026-07-17 — История из старого fitness.db не переносится

- Контекст: у продукта было предыдущее воплощение (обычный фитнес-трекер) со своей БД.
- Решение: начинаем с чистого листа, старую историю не мигрируем.
- Почему так: LIFE AI — концептуально другой продукт (аналитика жизни, а не трекер), перенос старых данных не оправдан.
- Альтернативы: миграция истории — отклонена.
- Когда пересмотреть: не пересматривать, если только не понадобятся конкретные архивные данные.

### 2026-07-17 — Без группового чата со сторонними ботами

- Контекст: рассматривался вариант интеграции с `@smartspeech_sber_bot` для группового сценария.
- Решение: личный чат с ботом остаётся приватным, без группового чата со сторонними ботами.
- Почему так: приватность данных о здоровье + вариант усложнял UX без явной пользы.
- Альтернативы: групповой чат с `@smartspeech_sber_bot` — отклонён.
- Когда пересмотреть: если появится явный запрос на групповой/семейный сценарий с отдельным согласием на приватность.

### 2026-09-02 — Тон бота: требовательный тренер вместо поддерживающего собеседника

- Контекст: Ольга сказала прямо — «мне нужно, чтобы он был поддерживающий, но достаточно строгий,
  чтобы держать меня в узде», «мне нужен результат, а не чтоб меня гладили по головке».
  Старый системный промпт буквально запрещал строгость: «запрещён любой осуждающий тон»,
  «приветствуется: ничего страшного, продолжаем, отличная работа».
- Решение: характер переписан на требовательного тренера — цифра и факт первыми, прямой вердикт
  по динамике, одно конкретное требование на завтра, похвала только за подтверждённый цифрами
  результат. Границы сохранены: критикуется режим, а не личность; без стыда, вины, диагнозов,
  выдуманных чисел и домыслов о физиологии; обращение всегда на «ты».
- Почему так: продукт не выполнял свою работу — он утешал вместо того, чтобы показывать картину.
- Альтернативы: «холодный аналитик» (без поддержки вовсе) и «жёсткий, с давлением» — отклонены
  самой Ольгой при выборе.
- Когда пересмотреть: если тон начнёт мешать вести дневник (записей станет меньше, а не больше).

### 2026-09-02 — Витрина данных: файлы в Telegram, а не веб-ссылка

- Контекст: нужны дашборд и таблица-первичка. Рассматривался живой веб-дашборд на VPS.
- Решение: HTML-дашборд и CSV-таблицы генерируются на сервере и отправляются в Telegram файлами.
- Почему так: данные о здоровье не публикуются, наружу не открывается ни один порт, файл всегда
  свежий на момент запроса и открывается без интернета (графики — инлайновый SVG, без библиотек).
- Альтернативы: HTTP-эндпоинт на VPS с токеном (открытый порт с медданными по HTTP без TLS) и
  автосинхронизация в Google Sheets (требует переноса личного OAuth Ольги на сервер) — отклонены.
- Когда пересмотреть: если понадобится живая ссылка, которую можно открыть с любого устройства
  без Telegram, или регулярная выгрузка именно в Google Таблицы.

### 2026-09-02 — Статистика считается кодом, а не моделью

- Контекст: бот отвечал, что данных нет, и мог назвать неверные цифры.
- Решение: `analytics/overview.py` считает всю статистику детерминированно (обычной арифметикой),
  и один и тот же результат идёт в промпт коуча, в команду `/stats`, в дашборд и в графики.
- Почему так: модель не должна считать то, что можно посчитать точно — иначе цифры в ответе и
  цифры в базе расходятся, и доверять аналитике нельзя.
- Альтернативы: отдавать модели сырые записи и просить посчитать — отклонено.
- Когда пересмотреть: не пересматривать. Новые метрики добавлять в overview.py, а не в промпт.
